🧪 Dummy Data & Testing Guide

Continuing after SSMS setup — inserting test data and verifying it end-to-end in VS Code

This continues directly from the SSMS Setup Guide. At this point SQL Server + SSMS are installed, connected, and AquaSafariDB exists. This guide covers inserting dummy data for all six modules and verifying it works through your VS Code backend and frontend — using your team's single shared-branch push/pull workflow.

1

Confirm your tables exist

Before inserting anything, run your Spring Boot app once from VS Code so Hibernate generates the tables from your team's @Entity classes. Then in SSMS, open a New Query on AquaSafariDB and run:

SELECT * FROM sys.tables;

Check the real table and column names here — they must match exactly what you use in the insert script below. If a module's entity hasn't been pushed yet, its table won't exist yet, and you'll need to skip that insert until it is.

2

Insert dummy data for all six modules

Run this in a New Query window on AquaSafariDB. Insert in this order so foreign keys resolve correctly:

USE AquaSafariDB;

-- 1. User/Admin Management
INSERT INTO users (name, email, password, role)
VALUES ('Test Customer', 'testuser@example.com', 'dummy_hashed_pw', 'CUSTOMER'),
       ('Test Admin', 'admin@example.com', 'dummy_hashed_pw', 'ADMIN');

-- 2. Boat Management
INSERT INTO boats (name, capacity, status)
VALUES ('Ocean Explorer', 12, 'AVAILABLE'),
       ('Sea Breeze', 8, 'MAINTENANCE');

-- 3. Trip Management
INSERT INTO trips (boat_id, trip_date, price)
VALUES (1, '2026-09-15', 5000.00),
       (2, '2026-09-20', 3500.00);

-- 4. Booking Management
INSERT INTO bookings (trip_id, user_id, status)
VALUES (1, 1, 'CONFIRMED'),
       (2, 1, 'PENDING');

-- 5. Payment Management
INSERT INTO payments (booking_id, amount, status)
VALUES (1, 5000.00, 'COMPLETED');

-- 6. Feedback & Reviews
INSERT INTO feedback (booking_id, user_id, rating, comment)
VALUES (1, 1, 5, 'Great trip!');
You don't need every table seeded to test your own module — Payment only needs users → boats → trips → bookings → payments. Skip feedback unless you're testing that module.

Save this script as database/seed-dummy-data.sql in the repo so everyone runs the same data and gets matching IDs (booking_id = 1, user_id = 1, etc.) on their own local instance.

3

Verify the data in SSMS

Confirm each table has rows before moving to VS Code:

SELECT * FROM users;
SELECT * FROM boats;
SELECT * FROM trips;
SELECT * FROM bookings;
SELECT * FROM payments;
SELECT * FROM feedback;
4

Test the backend in VS Code

  1. Open the backend folder in VS Code and confirm application.properties points to your local AquaSafariDB (from the SSMS setup guide).
  2. Run the app from the VS Code terminal: 
    ./mvnw spring-boot:run
  3. Check the terminal log for a successful startup with no connection or Hibernate errors, and confirm it's listening on localhost:8080.
  4. Use the VS Code Thunder Client or REST Client extension (or Postman) to hit your endpoint against the dummy data: 
    GET http://localhost:8080/api/payments
GET http://localhost:8080/api/payments/1

POST http://localhost:8080/api/payments
{
  "bookingId": 2,
  "amount": 3500.00,
  "status": "PENDING"
}
  5. Go back to SSMS and run SELECT * FROM payments; to confirm the new row landed correctly.
5

Test the frontend in VS Code

  1. Open the frontend folder in a second VS Code window (or workspace tab).
  2. Confirm your API base URL in the frontend code points to http://localhost:8080.
  3. Install dependencies if needed and start the dev server: 
    npm install
npm run dev
  4. Open the app at http://localhost:5173 and check that your Payment Management screens correctly display, create, and update the dummy rows from Step 2.
  5. Open the browser dev tools (Network tab) if data doesn't appear — confirm the requests are actually reaching localhost:8080 and returning data, not a CORS or 404 error.
If you get a CORS error in the browser console, add a @CrossOrigin annotation (or a global CORS config) on your Spring Boot controller allowing http://localhost:5173.
6

Push/pull on your shared single branch

Since the team is working on one branch (push → next person pulls → edits their part → pushes back), a few habits keep this from breaking:

  1. Always git pull before you start working — never edit on top of an outdated copy.
  2. Test your module locally against the dummy data (Steps 4–5) before you push, so you're not pushing broken code for the next person to inherit.
  3. Include the shared seed-dummy-data.sql in your commit if you added or changed any table/entity, so the next person can re-seed and test immediately after pulling.
  4. Push in small, working increments — don't leave the repo in a half-finished state before handing off.
  5. A quick message to the team ("pushed, safe to pull") avoids two people editing and pushing at the same time on a single branch, which is the main source of conflicts in this setup.
