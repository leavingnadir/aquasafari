2 Create & clone the GitHub repo

One member creates the repository on GitHub (e.g. named aquasafari) and adds the rest of the team as collaborators. Everyone else then clones it:

4 Set up the shared Azure SQL Database

The whole team connects to one shared Azure SQL Database — nobody installs SQL Server locally. Every member's Spring Boot app talks to the same cloud database over the internet, so data created through one module (e.g. a booking) is immediately visible to every other module (e.g. Payment) — no separate per-laptop setup, and no syncing needed.

4.1 — Create the Azure SQL Database (one member does this)

  1. Go to azure.microsoft.com/free and sign up for a free account (a student email often qualifies for Azure for Students, with no credit card required).
  2. In the Azure Portal, click Create a resource → Databases → SQL Database.
  3. Under Resource group, create a new one (e.g. aquasafari-rg).
  4. Under Database name, enter AquaSafariDB.
  5. Under Server, click Create new:
    • Server name: something globally unique, e.g. aquasafari-sql-server
    • Authentication method: Use SQL authentication
    • Server admin login: e.g. aquasafariadmin
    • Password: choose a strong password and share it with the team over a private channel (not committed to GitHub)
  6. Under Compute + storage, choose the free tier / Basic (lowest cost) option — more than enough for a coursework project.
  7. Click Review + create → Create. Deployment takes a few minutes.

4.2 — Allow the team to connect (firewall rules)

By default, Azure SQL blocks all external connections. Once the database is created:

  1. Open the SQL Server resource (not the database) in the Azure Portal → Security → Networking.
  2. Under Firewall rules, toggle Allow Azure services and resources to access this server to Yes.
  3. Click + Add your client IPv4 address to allow the machine you're on right now.
  4. Each teammate needs their own IP added too. Either:
    • Each member sends their public IP (from whatismyipaddress.com) to whoever manages the Azure resource, who adds a firewall rule per person, or
    • Add a wide rule (e.g. 0.0.0.0–255.255.255.255) for convenience during a coursework project — simpler, but less secure, so only do this short-term.
  5. Click Save.
University or public WiFi networks sometimes change your IP between sessions. If your connection suddenly stops working, check whether your IP changed and re-add it under Networking.

4.3 — Get the connection details

On the database resource page → Settings → Connection strings → copy the JDBC tab. It looks like:

jdbc:sqlserver://aquasafari-sql-server.database.windows.net:1433;database=AquaSafariDB;user=aquasafariadmin@aquasafari-sql-server;password={your_password};encrypt=true;trustServerCertificate=false;hostNameInCertificate=*.database.windows.net;loginTimeout=30;

4.4 — Point Spring Boot at the shared database

Every member updates their backend/src/main/resources/application.properties with the shared connection details:

spring.datasource.url=jdbc:sqlserver://aquasafari-sql-server.database.windows.net:1433;database=AquaSafariDB;encrypt=true;trustServerCertificate=false
spring.datasource.username=aquasafariadmin
spring.datasource.password=the_shared_password
spring.datasource.driver-class-name=com.microsoft.sqlserver.jdbc.SQLServerDriver

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.SQLServerDialect

Now when anyone runs their backend, they're reading and writing to the same database as everyone else — a booking created through one teammate's app is immediately visible to another's, with no per-laptop database to install or keep in sync.

4.5 — Connect via SSMS to browse/verify shared data

Open SSMS → Connect:

  • Server name: aquasafari-sql-server.database.windows.net
  • Authentication: SQL Server Authentication
  • Login / Password: the shared admin credentials from Step 4.1

You'll see the same AquaSafariDB and tables everyone else sees — useful for checking that another module's data actually landed correctly before you build against it.

4.6 — Do we need to share a schema.sql file?

No. This is the biggest difference from the manual-JDBC style used in labs like IT2140 (where you hand-write CREATE TABLE and run it yourself). Here, the schema is generated automatically by Hibernate from your @Entity classes (ddl-auto=update) — nobody writes or shares manual CREATE TABLE SQL. Since the whole team connects to the same Azure database, a table created from one member's entity is immediately visible to everyone else the moment they run their backend against it.

4.7 — Everyday run steps after pulling

These are the same every time, for every member:

# 1. Get the latest code
git pull origin <your-branch>

# 2. Run the backend — Hibernate updates the shared Azure schema automatically
cd backend
./mvnw spring-boot:run

# 3. Run the frontend
cd frontend
npm install
npm run dev

No per-laptop database install or setup is needed — as long as your application.properties points at the shared Azure server (Step 4.4), pulling and running is the whole workflow.

5 The database/ folder in the repo

You don't need a database/ folder for the schema itself — that's generated automatically by Hibernate from your @Entity classes (see Step 4.6), directly in the shared Azure database. But a small database/ folder at the repo root, alongside frontend/ and backend/, is useful for a few optional things your team will likely want anyway:

aquasafari/
├── frontend/
├── backend/
└── database/
    ├── seed-data.sql
    ├── schema-reference.sql
    └── application-example.properties
FilePurpose
seed-data.sqlSample INSERT statements (test users, boats, trips) everyone can run once against the shared Azure database so the demo has consistent data.
schema-reference.sqlOptional read-only reference: in SSMS, right-click the database → Tasks → Generate Scripts to export the current table structure. Useful for the design document/report — not needed to run the app.
application-example.propertiesA template with the Azure connection block and placeholder credentials, so new teammates know exactly what to fill in without guessing.
Never commit a real application.properties with actual Azure passwords to a public repo. Keep the real file listed in .gitignore, and only commit the *-example.properties template with placeholder values.

Adding Tailwind CSS

This only needs to be done once, by whoever scaffolds the frontend — everyone else just gets it via npm install after pulling.

cd frontend
npm install tailwindcss @tailwindcss/vite

Add the Tailwind plugin in vite.config.js:

import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})

Replace the contents of src/index.css with:

@import "tailwindcss";

Make sure src/main.jsx imports that CSS file:

import './index.css'

Then restart the dev server and test it by adding a Tailwind class to any element, e.g. <h1 className="text-3xl font-bold text-blue-600">:

npm run dev
Everyone on the team just needs to run npm install after pulling — the config files (vite.config.js, index.css) are already committed to the repo, so nobody else needs to repeat the setup.

9 Daily Git workflow

Follow this cycle every time you sit down to work on your module:

# 1. Make sure you're on your own branch
git checkout feature/payment-management

# 2. Pull the latest changes from dev before you start
git checkout dev
git pull origin dev
git checkout feature/payment-management
git merge dev

# 3. Do your work, then stage and commit
git add .
git commit -m "feat(payment): add payment status update endpoint"

# 4. Push to your remote branch
git push origin feature/payment-management
Commit small and often (a few times a day) rather than one huge commit at the end — it makes conflicts far easier to resolve.

10 Pull requests & merging into dev

  1. Push your feature branch to GitHub.
  2. On GitHub, open a Pull Request from your feature branch into dev.
  3. Ask at least one teammate to review it before merging — this catches bugs early and keeps everyone aware of what changed.
  4. Once approved, click Merge pull request on GitHub (or merge locally, see below).
  5. Periodically, once dev is stable and tested, merge dev into main for a release/demo milestone.

To merge locally instead of on GitHub:

git checkout dev
git pull origin dev
git merge feature/payment-management
git push origin dev

11 Handling merge conflicts

When Git can't automatically combine two changes, it marks the file with conflict markers:

<<<<<<< HEAD
your code
=======
their code
>>>>>>> feature/payment-management
  1. Open the flagged file(s) in your editor.
  2. Decide which version (or a combination) is correct, and remove the <<<<<<<, =======, >>>>>>> markers.
  3. Save the file, then:
git add <the-fixed-file>
git commit -m "fix: resolve merge conflict in PaymentService"
git push origin feature/payment-management
Conflicts are far less common if everyone works in their own package/folder (e.g. controller/PaymentController.java, controller/BookingController.java) and pulls dev often.

12 Commit message convention

Use a short prefix so the team can scan the history quickly:

PrefixUse for
feat:A new feature
fix:A bug fix
refactor:Code change with no behavior change
docs:Documentation only
test:Adding or fixing tests
chore:Build config, dependencies, cleanup

Example: git commit -m "feat(payment): integrate refund endpoint"

13 Git command cheat sheet

git status                     # what's changed
git log --oneline --graph --all  # visual history of all branches
git branch                     # list local branches
git branch -a                  # list local + remote branches
git checkout <branch>          # switch branches
git checkout -b <branch>       # create + switch to a new branch
git pull origin <branch>       # fetch + merge latest from remote
git push origin <branch>       # push local commits to remote
git merge <branch>             # merge another branch into current one
git stash                      # temporarily shelve uncommitted changes
git stash pop                  # bring stashed changes back
git diff                       # see unstaged changes
git reset --hard HEAD          # discard all local changes (careful!)
