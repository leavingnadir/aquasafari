2 Create & clone the GitHub repo

One member creates the repository on GitHub (e.g. named aquasafari) and adds the rest of the team as collaborators. Everyone else then clones it:

git config --global user.name "Your Name"
git config --global user.email "you@my.sliit.lk"

git clone https://github.com/<your-org-or-user>/aquasafari.git
cd aquasafari
Tip: agree on the folder layout (backend/ and frontend/) before anyone pushes code, so imports and paths line up.

4 Set up SQL Server & SSMS (on every laptop)

Unlike XAMPP/MySQL, SQL Server isn't a shared server the team connects to remotely — each of the 6 members installs and runs their own local SQL Server instance on their own laptop. Everyone's Spring Boot app talks to localhost, and all six databases end up with the same table structure because that structure is generated from the same JPA entity classes, which live in Git.

4.1 — Install (each member does this once)

  1. Download and install SQL Server — Developer or Express edition (both free) — from Microsoft's site.
  2. During setup, choose Mixed Mode Authentication and set an sa password. Agree on the same password as a team so everyone's application.properties looks identical.
  3. Install SQL Server Management Studio (SSMS) separately if it isn't bundled — it's the GUI tool used to browse and query the database.

4.2 — Create the database (each member does this once)

  1. Open SSMS and connect: Server name = localhost (or localhost\SQLEXPRESS for the Express edition), Authentication = SQL Server Authentication, Login = sa, with the password you set.
  2. In Object Explorer, right-click Databases → New Database.
  3. Name it AquaSafariDB — use this exact name on all six laptops.

4.3 — Connect Spring Boot to SQL Server

In backend/pom.xml, make sure the SQL Server JDBC driver is a dependency (add it if it isn't there, or if the project was generated with the MySQL driver instead):

<dependency>
    <groupId>com.microsoft.sqlserver</groupId>
    <artifactId>mssql-jdbc</artifactId>
    <scope>runtime</scope>
</dependency>

Add this to backend/src/main/resources/application.properties:

spring.datasource.url=jdbc:sqlserver://localhost:1433;databaseName=AquaSafariDB;encrypt=false;trustServerCertificate=true
spring.datasource.username=sa
spring.datasource.password=your_agreed_password
spring.datasource.driver-class-name=com.microsoft.sqlserver.jdbc.SQLServerDriver

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.SQLServerDialect
With ddl-auto=update, Hibernate builds the tables straight from your @Entity classes the first time each person runs the app — nobody has to write or share manual CREATE TABLE SQL. As long as everyone git pulls the same entity classes, all six local databases end up structurally identical.
If SQL Server is installed on Windows and you named the instance during setup (common with Express, e.g. SQLEXPRESS), your JDBC URL needs the instance name instead of the port, e.g.
jdbc:sqlserver://localhost\\SQLEXPRESS;databaseName=AquaSafariDB;encrypt=false;trustServerCertificate=true — check under SSMS → server properties if you're not sure which one applies.
Never commit real passwords to a public GitHub repo. For a private academic repo, sharing one agreed sa password across the team is common practice — for anything beyond coursework, use a per-member application-local.properties (git-ignored) or environment variables instead.

4.4 — Verify the data (any member)

After running the backend once, refresh the database in SSMS and expand AquaSafariDB → Tables — your JPA entities should now appear as tables. You can inspect rows with:

SELECT * FROM Payment;

6 Run the Spring Boot backend

cd backend

# Windows
mvnw.cmd clean install
mvnw.cmd spring-boot:run

# macOS / Linux
./mvnw clean install
./mvnw spring-boot:run

The API should now be running at http://localhost:8080. Test a simple endpoint in Postman or your browser to confirm it started correctly.

7 Set up & run the React frontend

If the frontend hasn't been created yet, one member scaffolds it once with Vite:

npm create vite@latest frontend -- --template react
cd frontend
npm install
npm install axios

Everyone else just installs dependencies after cloning:

cd frontend
npm install
npm run dev

The frontend runs at http://localhost:5173 and should call the backend at http://localhost:8080/api/....

Adding Tailwind CSS

This only needs to be done once, by whoever scaffolds the frontend — everyone else just gets it via npm install after pulling.

cd frontend
npm install tailwindcss @tailwindcss/vite

Add the Tailwind plugin in vite.config.js:

import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
})

Replace the contents of src/index.css with:

@import "tailwindcss";

Make sure src/main.jsx imports that CSS file:

import './index.css'

Then restart the dev server and test it by adding a Tailwind class to any element, e.g. <h1 className="text-3xl font-bold text-blue-600">:

npm run dev
Everyone on the team just needs to run npm install after pulling — the config files (vite.config.js, index.css) are already committed to the repo, so nobody else needs to repeat the setup.

8 Daily Git workflow

Follow this cycle every time you sit down to work on your module:

# 1. Make sure you're on your own branch
git checkout feature/payment-management

# 2. Pull the latest changes from dev before you start
git checkout dev
git pull origin dev
git checkout feature/payment-management
git merge dev

# 3. Do your work, then stage and commit
git add .
git commit -m "feat(payment): add payment status update endpoint"

# 4. Push to your remote branch
git push origin feature/payment-management
Commit small and often (a few times a day) rather than one huge commit at the end — it makes conflicts far easier to resolve.

9 Pull requests & merging into dev

  1. Push your feature branch to GitHub.
  2. On GitHub, open a Pull Request from your feature branch into dev.
  3. Ask at least one teammate to review it before merging — this catches bugs early and keeps everyone aware of what changed.
  4. Once approved, click Merge pull request on GitHub (or merge locally, see below).
  5. Periodically, once dev is stable and tested, merge dev into main for a release/demo milestone.

To merge locally instead of on GitHub:

git checkout dev
git pull origin dev
git merge feature/payment-management
git push origin dev

10 Handling merge conflicts

When Git can't automatically combine two changes, it marks the file with conflict markers:

<<<<<<< HEAD
your code
=======
their code
>>>>>>> feature/payment-management
  1. Open the flagged file(s) in your editor.
  2. Decide which version (or a combination) is correct, and remove the <<<<<<<, =======, >>>>>>> markers.
  3. Save the file, then:
git add <the-fixed-file>
git commit -m "fix: resolve merge conflict in PaymentService"
git push origin feature/payment-management
Conflicts are far less common if everyone works in their own package/folder (e.g. controller/PaymentController.java, controller/BookingController.java) and pulls dev often.

11 Commit message convention

Use a short prefix so the team can scan the history quickly:

PrefixUse for
feat:A new feature
fix:A bug fix
refactor:Code change with no behavior change
docs:Documentation only
test:Adding or fixing tests
chore:Build config, dependencies, cleanup

Example: git commit -m "feat(payment): integrate refund endpoint"

12 Git command cheat sheet

git status                     # what's changed
git log --oneline --graph --all  # visual history of all branches
git branch                     # list local branches
git branch -a                  # list local + remote branches
git checkout <branch>          # switch branches
git checkout -b <branch>       # create + switch to a new branch
git pull origin <branch>       # fetch + merge latest from remote
git push origin <branch>       # push local commits to remote
git merge <branch>             # merge another branch into current one
git stash                      # temporarily shelve uncommitted changes
git stash pop                  # bring stashed changes back
git diff                       # see unstaged changes
git reset --hard HEAD          # discard all local changes (careful!)
